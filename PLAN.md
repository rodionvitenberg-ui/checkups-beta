# PLAN.md — Ревью и план улучшений WebDoc.life

Полный разбор проекта: найденные ошибки, недоработки и недочёты, сгруппированные по приоритетам. Каждый пункт — с локацией, описанием проблемы и конкретным предлагаемым исправлением.

## 🔴 Критично (безопасность / потеря данных / деньги)

### C1. Неиспользуемый API-ключ `RESEND_API_KEY` (удалён)
**Где:** ранее `backend/config/settings.py` (блок `ANYMAIL`)
**Проблема:** Ключ был захардкожен в репозитории, хотя `EMAIL_BACKEND` — обычный SMTP, то есть ключ не использовался.
**Статус:** ✅ Удалён. Блок `ANYMAIL` выпилен из `settings.py`, `django-anymail` удалён из `requirements.txt` и `backend/requirements.txt`. Почта ходит только через SMTP. Секреты — только через `os.getenv(...)`.

### C2. Гостевой эндпоинт отдаёт чужие анализы без авторизации (`auth=None`)
**Где:** `backend/core/api.py`
- `get_analysis_result` (`/analyses/{uid}`) — `auth=None`, отдаёт `ai_result` по любому UID.
- `download_analysis_file` (`/analyses/{uid}/download`) — `auth=None`, отдаёт **оригинал файла**.
- `stream_analysis_status` — пусть и менее чувствителен, тоже открыт.

**Проблема:** UID — это UUID v4, но это не секрет. Любой, у кого оказалась ссылка (пересланная, из логов, из истории браузера), получает полную расшифровку и исходный файл с персональными данными. Это утечка медицинских данных.
**Исправление:** Ввести «claim-токен» или проверку владения. Минимально: для гостевых анализов генерировать одноразовый секрет и отдавать ссылку вида `/analyses/{uid}?token=...`. Для `download` — строго авторизация владельца либо временный signed URL. Убрать `auth=None` с `download` и добавить проверку `analysis.user == request.user` (плюс отдельный гостевой claim-флоу).

### C3. Липкий `assert`-флоу: `create_payment` может повторно дебетовать/создавать дубли
**Где:** `backend/premium/api.py:166-188`
**Проблема:** Каждый клик по «Оформить PRO» создаёт новую `Transaction` и новую заявку в Cryptomus. Нет идемпотентности: повторный клик/обновление страницы — несколько pending-ордеров.
**Исправление:** Хранить активный pending-ордер на юзера (unique на `user`+`status='pending'`), либо `order_id` генерировать детерминированно (например, `pro_{user.pk}_{месяц}`), чтобы повторный вызов возвращал тот же платёж.

### C4. Webhook Cryptomus: подпись проверяется, но платёж можно подделать при слабом `order_id`
**Где:** `backend/premium/api.py:134-218`, `backend/premium/services.py:140-152`
**Проблема:**
1. `verify_webhook` пересобирает подпись из распарсенного JSON (`data`), тогда как Cryptomus подписывает **raw body**. Порядок ключей/экранирование могут отличаться → легитимные webhook'и отклоняются, либо проверка неэффективна. В текущем виде `request.body` парсится через `json.loads`, исходные байты теряются.
2. `Transaction.order_id` — `uuid4`, но статус проверяется только на `== 'paid'`, нет защиты от повторного начисления (`tx.status != 'paid'` — есть, но поле `pro_expires_at` просто перезаписывается на now+30, «не продлевается»).
**Исправление:** Передавать в `verify_webhook` сырой `request.body` (bytes) и считать MD5 по нему. Продлевать подписку от текущего `pro_expires_at`, а не от `now()`.

### C5. `DEBUG`/`SECRET_KEY` без значений по умолчанию → падение в рантайме
**Где:** `backend/config/settings.py:28-33`
```python
SECRET_KEY = os.getenv('SECRET_KEY')
```
**Проблема:** Если `.env` отсутствует, `SECRET_KEY=None` и проект упадёт (а `ALLOWED_HOSTS=''.split(',')` даст `['']`). Для dev-среды нет безопасного фолбэка.
**Исправление:** Добавить dev-fallback под `DEBUG`, либо явно валидировать наличие секрета с понятным сообщением об ошибке.

## 🟠 Высокий приоритет (корректность, надёжность)

### H1. Пагинация LLM-ключей разъезжается при ретраях → IndexError / бесконечный цикл
**Где:** `backend/analysis/services.py:56-100`, `backend/premium/services.py:73-102`
**Проблема:**
- `_call_llm_with_fallback` делает `max_retries = len(api_keys) * 2`, но `_switch_key()` двигает `current_key_idx` только на 1 за раз. После исчерпания ключей `_switch_key()` возвращает `False`, но `current_key_idx` уже на последнем — при следующей ошибке вызов `self.api_keys[self.current_key_idx]` валиден, но ключей больше нет → `time.sleep(20)` и тот же ключ снова в цикле.
- Если ключей 0 (бывает — `ChatAssistant` не ставит `DUMMY_KEY` fallback в отличие от `AnalysisPipeline`), то `api_keys[0]` даст `IndexError`.
- `_get_client()` обращается к `api_keys[self.current_key_idx]` без проверки границ.
**Исправление:** Вынести общую логику LLM-клиента с fallback в один переиспользуемый класс (см. раздел «Архитектура», A2). Инкрементировать индекс по кругу с остановкой после полного круга, проверять пустой список ключей и бросать понятную ошибку.

### H2. Лимит «2 анализа в день» считается неверно при повторной обработке
**Где:** `backend/core/api.py:226-249`, `upload_analysis:357-370`, `reanalyze:443-455`
**Проблема:**
- В `claim_verify` лимит считается по `todays_analyses.index(pending) + 1` — это **позиция в общем списке анализов за день**, а не число реально запущенных. При чистом flow это случайно совпадает, но с reanalyze/падающими анализами — нет.
- В `upload_analysis` и `reanalyze` считается `filter(created_at__date=today).count()` — но `reanalyze` создаёт копию с `created_at=now`, значит каждый пересчёт съедает лимит (reanalyze — это ведь повторный анализ по тому же бланку).
- Логика лимита продублирована в 3 местах → рассинхрон.
**Исправление:** Один хелпер `enforce_daily_limit(user)` / `count_todays_analyses(user)`, считать именно «обработанных сегодня», а не позицию. Вынести лимиты (`FREE=2`, `PRO=10`) в константы.

### H3. `OptionalJWTAuth` глотает все исключения → небезопасная «тихая» авторизация
**Где:** `backend/core/api.py:77-87`
```python
def __call__(self, request):
    try:
        return super().__call__(request)
    except Exception:
        return None
```
**Проблема:** При любом сбое JWT (валидный, но протухший/искажённый) юзер трактуется как аноним. Сам класс объявлен, но в эндпоинтах фактически не используется (везде `auth=None` + ручной разбор заголовка). Это лишний код-ловушка.
**Исправление:** Удалить класс, если он не используется; заменить ручной разбор `Authorization` в `upload_analysis` на нормальный `auth=OptionalJWTAuth()` (или наоборот) — единый механизм.

### H4. POST-стрим чата: сообщение пользователя сохраняется, ответ ИИ — только если не оборвался стрим
**Где:** `backend/premium/api.py:85-164`
**Проблема:** При обрыве SSE (юзер закрыл вкладку, сеть упала) `ChatMessage` юзера уже сохранён, а ответа нет; `contains` в генераторе после `yield` не выполнится. Нарушается целостность истории.
**Исправление:** Собирать ответ ИИ в накопителе с `try/finally`, либо сохранять ответ по факту получения каждого чанка и помечать «не завершён». Как минимум оборачивать сохранение в `finally`.

### H5. Стримы `status` и `chat` спамят БД и не имеют таймаутов
**Где:** `backend/core/api.py:473-496` (status-stream), `premium/api.py:138-164` (chat stream)
**Проблема:** `status-stream` делает `SELECT` каждые 2 секунды на каждое открытое соединение — при 100+ ожидающих это постоянная нагрузка. Нет обработки разрыва (генератор продолжит летать, пока клиент не оборвёт).
**Исправление:** Использовать Redis pub/sub или `django-channels`/`SSE` с heartbeat; как минимум — увеличить интервал + добавить `select_for_update`/лимит. Для MVP: оставить poll, но добавить `+ timeout` и не опрашивать после финального статуса.

## 🟡 Средний приоритет (качество, согласованность типов, UX)

### M1. `AnalysisResponseSchema.ai_result` объявлен `None=...` и отдаёт валидные данные, но `SummarySchema.is_critical`/`general_comment` — обязательные
**Где:** `backend/core/schemas.py:11-14, 92-107`
**Проблема:** `summary` обязателен внутри `AIResultSchema`, но LLM может вернуть `summary: null` (напр., при падении). Тогда сериализация 500-й. На фронте `AIResult.summary` тоже обязательный (`frontend/lib/types.ts:38-41`), хотя backend может отдать `null`.
**Исправление:** Сделать `summary` и его поля опциональными на обеих сторонах, добавить защитную валидацию результата LLM до сохранения (`ai_result` — это JSONField, сюда можно записать что угодно).

### M2. Несогласованность типов параметров сериализаторов
**Где:** `backend/core/api.py:135` и `frontend/lib/types.ts:16-18`
- `extracted_name` есть в TS, но отсутствует в backend `PatientMetadataSchema`.
- `UpdateProfileSchema` требует `full_name: str` (обязательное), но `updateProfile` на фронте может слать только частичные поля → 422.
- `AIIndicator.value` на фронте `string`, но `save_atomic_indicators` пытается распарсить в `float` — допускается несоответствие.
**Исправление:** Синхронизировать схемы (по правилу проекта «types sync»): `full_name` сделать опциональным в `UpdateProfileSchema`, `value` — `Optional[str]`, добавить/убрать `extracted_name` согласно реальному контракту.

### M3. Обработка ошибок и «чистые» 500
**Где:** по всему `core/api.py`, `premium/api.py`
**Проблема:**
- `except Exception ... print` в email-блоках и в задаче — реальность маскируется.
- `fail_silently=True` — письма с паролем/кодом не доходят без следа. Регистрация с «пароль-почта» при недоступной почте молча оставляет юзера без пароля/кода (он не знает, как войти).
- Возврат `HttpError` из Ninja, но фронт местами ждёт `data.message`, местами `data.status`.
**Исправление:** Единый формат ошибки (`{"message": ..., "code": ...}`), логировать письма, не `fail_silently`, и добавить Sentry (уже в зависимостях — `sentry-sdk`, но не инициализирован).

### M4. `status-stream` блокирует nginx/gunicorn из-за `time.sleep` в генераторе
**Где:** `backend/core/api.py:493-494`
**Проблема:** `time.sleep(2)` в синхронном генераторе — при gunicorn с синхронными воркерами весь процесс спит, блокируя остальные запросы. Воркер не должен замирать на 2 секунды на поток.
**Исправление:** Перейти на async-представление (`async def`/`daphne`) или использовать `StreamingHttpResponse` с async-генератором + `asyncio.sleep`. Как минимум не использовать синхронный `time.sleep`.

### M5. Передача файлов между бэкендом и celery-воркером по локальному пути
**Где:** `backend/core/tasks.py:105` (`analysis.file.path`)
**Проблема:** `process_analysis_task` читает файл через `.path` — это работает только при общем volume (`backend_media`). Если перейти на S3/R2 (упоминается в комментариях), `.path` упадёт. Также OCR-зависимости (`pdf2image` требует `poppler-utils`, `pytesseract` требует `tesseract`) не задекларированы в Dockerfile явно для poppler.
**Исправление:** Читать файл через `.read()`/поток из storage API; для `pdf2image` — явно проверять `poppler-utils` в Dockerfile.

### M6. `frontend/requirements.txt` — мусорная копия backend-зависимостей
**Где:** `frontend/requirements.txt` (136 строк Python-пакетов)
**Проблема:** Файл Python-зависимостей попал во frontend (вероятно, случайная копия). Для Node-проекта не нужен, сбивает с толку и может быть ошибочно использован.
**Исправление:** Удалить файл.

### M7. Googl Analytics ID — заглушка
**Где:** `frontend/app/[locale]/layout.tsx:112`
```tsx
<GoogleAnalytics gaId="G-XXXXXXXXXX" />
```
**Проблема:** Плейсхолдер. Либо подставить реальный ID через env, либо убрать.
**Исправление:** `process.env.NEXT_PUBLIC_GA_ID` с фолбэком в `undefined` (не рендерить, если нет).

## 🟢 Низкий приоритет / косметика (можно отложить)

### L1. `DEBUG=True` отдаёт статику через URL, но в проде используется `CompressedManifestStaticFilesStorage`
**Где:** `backend/config/settings.py:161`, `config/urls.py:15-17`
**Проблема:** Мелкая — в dev проявляется конфликт при `collectstatic` + `DEBUG` (manifest-хэши). Не критично.
**Исправление:** Настроить `STORAGES` Django 4.2+ вместо `STATICFILES_STORAGE` (устаревшая настройка), либо оставить как есть.

### L2. Дубль импортов и «мёртвый» код
**Где:** `backend/core/api.py` (импорты `JWTAuth`, `HttpBearer`, `Form`, `schema` дублируются; `import time`, `random`, `transaction` — часть не используется), `frontend/lib/api.ts` и т.д.
**Проблема:** Неиспользуемые импорты и двойные импорты (`from ninja_jwt.authentication import JWTAuth` дважды).
**Исправление:** Прогнать `ruff` / `flake8` по backend, `eslint` по фронту (eslint уже настроен, но не запускался — см. L4).

### L3. Комментарии-«заглушки» с незавершёнными значениями
**Где:** `backend/premium/services.py:123-124` — `https://твой_домен/...`, `backend/config/settings.py:279`, `frontend/app/[locale]/layout.tsx`.
**Проблема:** Несобранные URLs.
**Исправление:** Заменить на реальные домены/переменные окружения.

### L4. Тесты пустые, но ESLint/Playwright декларированы
**Где:** `backend/core/tests.py`, `backend/analysis/tests.py`, `backend/premium/tests.py` (заглушки), `frontend/tests/example.spec.ts`
**Проблема:** «Тесты» = `# Create your tests here`. Учитывая объём критичной логики (лимиты, оплата, привязка анализов), отсутствие тестов рискованно.
**Исправление:** Добавить минимальные юнит-тесты на: `save_atomic_indicators` (парсинг дат), `claim_verify` (привязка), лимиты, `process_analysis_task` (mock LLM). Для фронта — smoke-тест Playwright переписать на реальный flow.

### L5. `docker-compose.yml`: нет сервиса для миграций
**Где:** `docker-compose.yml`
**Проблема:** `backend` сразу запускает gunicorn (`manage.py` не вызывается на миграции), поэтому при пустой базе БД не будет схемы. Celery стартует без воркера миграции.
**Исправление:** Добавить `command: sh -c "python manage.py migrate --noinput && gunicorn ..."` либо отдельный one-shot сервис `migrate`.

### L6. Гигантский `requirements.txt` с пакетами, не использующимися в проекте
**Где:** `requirements.txt` (137 строк, включая `google-genai`, `anthropic`, `groq`, `pymorphy3`, `standardwebhooks`, `svix` и др.)
**Проблема:** Много неиспользуемых зависимостей (три отдельных LLM-провайдера, плюс DeepSeek). Раздувает образ, увеличивает поверхность атаки.
**Исправление:** Оставить только реально используемые (в рамках ponytail: не тянем вещи впрок). Составить минимальный `requirements.in` + сгенерировать замороженный `requirements.txt`.

## 🏗 Архитектура (codebase-design / domain-modeling)

### A1. Доменная терминология не зафиксирована, термины размыты
**Где:** нет `CONTEXT.md`, нет единого глоссария.
**Наблюдение:** В коде смешиваются: «профиль пациента» и «орфан-профиль», «анализ» (MedicalAnalysis) и «показатель» (AnalysisIndicator), «пересчёт» = «reanalyze» = копия анализа. Нет единого имени для гостевого флоу «claim».
**Рекомендация:** Создать `CONTEXT.md` с глоссарием и зафиксировать ADR (см. A3).

### A2. Логика LLM-клиента продублирована в двух модулях
**Где:** `backend/analysis/services.py` (`AnalysisPipeline`) и `backend/premium/services.py` (`ChatAssistant`)
**Проблема:** Почти одинаковый код: `api_keys`, `_get_client`, `_switch_key`, `_get_prompt`, base_url/model_name. Различие — только в параметрах вызова (stream / json_mode). Это нарушение DRY и рассинхрон (например, `ChatAssistant` не имеет `DUMMY_KEY` fallback и не умеет `AI_API_KEY` без индекса — уже разошлись).
**Рекомендация:** Вынести общий `LLMClient` (провайдер-интерфейс: `complete()`/`stream()`) в отдельный модуль, а `AnalysisPipeline` и `ChatAssistant` сделать тонкими обёртками. Это «deep module»: маленький интерфейс (`complete`, `stream`), сложная реализация внутри (пул ключей, retry, fallback, ошибки).

### A3. Смешение «интерпретации» и «сохранения» в одном пайплайне
**Где:** `backend/analysis/services.py` + `backend/core/tasks.py`
**Наблюдение:** `AnalysisPipeline.run_pipeline` отвечает и за вызов LLM, и за приём структуры результата. `save_atomic_indicators` живёт в `core/services.py`. Размазанная ответственность: extract/interpret/save/aggregate.
**Рекомендация:** Разделить на чистые модули: `DocumentExtractor` (OCR) → `Anonymizer` → `AnalysisInterpreter` (LLM) → `IndicatorRepository` (сохранение). Каждый — с одним интерфейсом (seam), лёгким для теста.

### A4. `AnalysisPipeline` хрупок: парсинг дат и индикаторов через regex поверх JSON-дампа
**Где:** `backend/analysis/services.py:117-145`, `core/services.py:20-53`
**Проблема:**
- «Агрессивный поиск даты» через `json.dumps(ai_result)` + regex — хрупко (завязка на строковое представление, неопределённость форматов дат).
- `extracted_date` одновременно используется и как дата сбора биоматериала, и как дата анализа — конфликт значений.
**Рекомендация:** Явно валидировать выходной JSON LLM через Pydantic-схему (уже есть `AIResultSchema`) и обогащать контекст из проверенных полей, а не regex. Если даты нет — спокойно падать на дефолт без «агрессивного поиска».

### A5. «Гостевой» флоу (orphan → claim) — неявный и хрупкий
**Где:** `backend/core/api.py` claim-эндпоинты, `PatientProfile.user=null`
**Наблюдение:** Загрузка гостем создаёт `PatientProfile` и `MedicalAnalysis` с `user=None`; затем `claim_verify` «чинит» привязку (удаляет орфана, перепривязывает). Логика в 5-6 ветках, трудночитаемая, есть риск потери данных при `delete()`.
**Рекомендация:** Выделить явный доменный объект/сервис `ClaimService` с методами `claim(analysis_uids, email)` и `verify(...)`, а orphan-профили обрабатывать централизованно (не удалять агрессивно, а помечать `is_orphan`/переносить).

### A6. Singleton-модель `ChatSettings` реализована криво
**Где:** `backend/premium/models.py:95-118`
**Проблема:** `save()` перезаписывает `self.pk = 1`, простое решение, которое работает, но не потокобезопасно (конкурентный `get_or_create` может создать нулевую запись или гонку).
**Рекомендация:** Либо отдельная настройка в `django-constance` (проще, не тянем лишний пакет — см. ponytail), либо валидация на уровне БД (constraint). Как минимум документировать.

### A7. `PatientProfile.__str__` и `get_gender_display` имеют проблемы при `user=None`

## Оценка по ponytail (over-engineering)

Ключевые лишние вещи:
- **Три неиспользуемых LLM-провайдера** в `requirements.txt` — удалить.
- **`frontend/requirements.txt`** — удалить.
- **`OptionalJWTAuth`** класс — объявлен, не используется (ручной парсинг токена вместо него).
- **`SystemAnalytics` (proxy) + шаблон** — дашборд через proxy-модель дублирует то, что можно считать обычными `queryset`-методами в `admin`; proxy-модель необязательна.
- **`sharedFileStore` в `zustand`** — глобальный стор ради проброса файлов между компонентами можно заменить локальным состоянием/URL-параметром.

Итого возможное сокращение — **~250-350 строк и несколько неиспользуемых пакетов** без потери функциональности.
